# fitness_agent
# Fitness Agent｜基于 OpenClaw 的微信健康管理 Agent 产品原型

一个基于 OpenClaw 工作流设计、以微信为主要交互入口的 Fitness 垂直 Agent 原型。

它不是一个普通 calorie tracker，也不是一个 prompt-only chatbot。它关注的是：当用户训练、吃超、断记、社交饮食、表达偏好或需要恢复节奏时，Agent 如何用更低压力、更有上下文、更少打扰的方式帮助用户接回来。

Fitness Agent 将单点热量记录扩展为训练、饮食、恢复、图片记录、候选记忆、个性化推荐和温和召回的连续健康管理体验。

## 1. 为什么做这个项目

传统热量记录工具通常只解决两个问题：

* 今天吃了什么；
* 还剩多少热量。

但真实健康管理更复杂。用户更常遇到的是：

* 今天晚上训练，白天应该怎么吃；
* 练后到底要不要补碳水和蛋白；
* 吃超以后不想记录，怎么重新接回节奏；
* 社交饮食、喝酒、出差后如何恢复；
* 哪些输入只是当日状态，哪些才应该成为长期偏好；
* 用户断记以后，Agent 应该什么时候提醒，什么时候不该打扰。

所以这个项目没有把重点放在“更精确地算热量”，而是放在一个更贴近真实行为的问题上：

> 当用户偏离计划以后，Agent 能不能用更温和、更可执行的方式，把用户接回健康管理节奏？

---

## 2. 产品目标

Fitness Agent 主要验证五个产品问题：

1. 如何从单次饮食记录升级为训练—饮食—恢复闭环；
2. 如何在吃超、断记、社交饮食等场景下设计低压力恢复体验；
3. 如何设计候选记忆机制，避免把单次表达误记为长期偏好；
4. 如何让确认后的记忆真正影响后续推荐；
5. 如何基于上下文做温和召回，防止用户一次吃超后彻底放弃记录。

---

## 3. 核心体验

### 训练日饮食规划

用户在微信中输入：

```text
今天晚上练臀，怎么吃？
```

Agent 会结合训练日场景，给出练前、练后和晚餐建议。

产品重点不是简单计算热量，而是理解训练时间、训练部位和恢复需求，让用户知道今天怎么吃更适合训练和恢复。

---

### 吃超后的低压力恢复

用户输入：

```text
我今天吃爆了，不想记了。
```

Agent 不会要求用户补齐所有记录，也不会建议惩罚性运动，而是把用户拉回一个更小、更容易执行的动作：

```text
不用补前面的记录。
不用靠不吃饭来补偿。
下一餐正常吃，先回到高蛋白 + 蔬菜 + 少量主食。
明天先记录一餐，就算重新接上节奏。
```

产品重点是把用户从“失败叙事”拉回“下一餐接回来”的可执行路径。

在健康管理场景里，一次吃超本身不是最大问题。真正的问题是用户因此开始自暴自弃，觉得“反正已经失败了”，然后彻底中断记录和训练节奏。

---

### 图片饮食粗记录

用户可以在微信中发送食物图片，并配一句：

```text
午餐
```

Agent 会给出粗粒度识别、热量区间、置信度和不确定因素。

这里的产品定位不是“精准识别每一克食物”，而是降低用户记录门槛。相比让用户手动输入每个食材，图片记录更适合作为一种低成本启动方式。

因此 Agent 会明确告诉用户：

* 这是粗估；
* 哪些因素不确定；
* 用户可以继续纠正；
* 不制造高精度幻觉。

---

### 周度轻量复盘

Agent 可以根据本周记录生成低压力周报，例如：

```text
这周你完成了 3 次训练，其中臀腿 2 次、背部 1 次。

饮食记录 5 天，有些天只记录了一部分，也可以先用来观察节奏。

下周先只抓一个小动作：训练日下午提前安排一个轻量加餐。
```

产品重点不是追求完美记录，而是帮助用户看到节奏，并给出一个可执行的下一步。

---

## 4. Agent 架构

Fitness Agent 被设计为一个垂直 Agent，而不是一个巨大 prompt。

整体结构可以理解为：

```text
微信用户输入
   |
OpenClaw 工作流路由
   |
Fitness Agent
   |
意图理解
   |
场景处理
   |
状态 / 记忆 / 召回
   |
微信回复或主动触达
```

核心模块包括：

```text
Fitness Agent
  |
  +-- 意图路由
  |     - 训练日饮食
  |     - 练后恢复
  |     - 吃超恢复
  |     - 周度复盘
  |     - 偏好记忆
  |     - 召回开启 / 关闭
  |
  +-- 状态管理
  |     - 当日饮食状态
  |     - 训练状态
  |     - 周度聚合
  |     - 用户偏好
  |
  +-- 记忆系统
  |     - 候选记忆
  |     - 确认机制
  |     - 长期偏好
  |     - 推荐行为生效
  |
  +-- 多模态输入
  |     - 食物图片粗记录
  |     - 热量区间
  |     - 置信度
  |     - 不确定因素
  |
  +-- 温和召回
        - 用户主动开启
        - 上下文判断
        - 静默时段
        - 重复保护
        - 低压力提醒
```

这个架构的核心思想是：把 Agent 的“会聊天”拆成更可控的产品能力，包括理解场景、维护状态、沉淀记忆、控制打扰和接入微信触达。

## 5. 记忆机制设计

健康管理里的记忆不能随便写入。

用户的一句话可能只是当日状态，也可能是长期偏好，还可能是情绪表达。如果 Agent 把所有内容都自动记成长期记忆，会很容易产生错误个性化。

所以 Fitness Agent 将记忆拆成四个阶段：

```text
用户输入
-> 候选记忆
-> 确认
-> 长期偏好
-> 影响后续推荐
```

例如：

```text
今天吃了一碗牛肉面。
```

这只是当日饮食记录，不应该进入长期偏好。

而：

```text
以后练前别推荐酸奶，我会胃不舒服。
```

这是明确的偏好或安全边界，可以进入候选记忆。

经过确认后，这条偏好才会成为 active preference。之后用户再次问：

```text
今天晚上练臀，怎么吃？
```

Agent 会在推荐中避开酸奶，改用香蕉、小饭团、豆浆、鸡蛋、豆腐等替代选项。

这个闭环证明：记忆不是静态存储，而是真的改变了 Agent 后续行为。

## 6. 温和召回策略设计

Recall 的设计目标不是“提醒用户少吃”，而是防止用户在一次吃超、断记或社交饮食后进入自暴自弃状态。

支持的召回场景包括：

* 吃超后中断；
* 连续未记录；
* 训练日前未安排饮食；
* 练后未恢复；
* 社交饮食后需要 reset；
* 低数据状态下的轻量重启。

召回文案遵循低压力原则：

```text
不用补前面的记录。
你只要从今天一餐开始，回我一句吃了什么，我就帮你重新接上。
```

产品边界是：

* 不说“你又忘了”；
* 不要求补齐历史记录；
* 不建议惩罚性运动；
* 不制造羞耻感；
* 不默认主动推送；
* 只在用户开启后触达；
* 通过静默时段、冷却时间和重复保护控制打扰。

这里的关键不是“能不能推送消息”，而是 Agent 是否能判断什么时候该轻轻拉用户一把，什么时候应该保持安静。

## 7. OpenClaw 与微信交互

Fitness Agent 基于 OpenClaw 工作流设计，主要交互方式是微信。

微信承担的是用户最自然的输入入口：

* 用户可以直接发一句“今天晚上练臀，怎么吃”；
* 可以在吃超后发一句“我不想记了”；
* 可以发送食物图片进行粗记录；
* 可以表达长期偏好；
* 也可以开启或关闭召回。

OpenClaw 负责承接微信消息、路由到 Fitness Agent，并在需要时通过微信通道完成回复或触达。

这种设计让 Fitness Agent 更接近一个长期陪伴型 Agent，而不是一个需要用户打开 App、进入页面、填写表单的记录工具。

---

## 8. 当前边界

Fitness Agent 当前不是：

* 医疗建议系统；
* 高精度食物识别系统；
* 生产级营养数据库；
* 默认自动推送系统；
* 不经用户授权就主动发消息的系统；
* 把所有微信聊天上下文都写入长期记忆的系统。

当前版本更关注的是：如何设计一个有状态、有记忆、有召回边界、以微信为主要交互入口的垂直健康管理 Agent。

---

## 9. 项目亮点

* 基于 OpenClaw 框架设计微信优先的垂直健康管理 Agent；
* 从 calorie tracking 升级为训练—饮食—恢复—召回闭环；
* 设计非羞辱式 lapse recovery，帮助用户在吃超后接回节奏；
* 区分当日状态、候选记忆和长期偏好；
* 记忆确认后能真正改变后续推荐；
* 支持微信内图片粗记录，降低饮食输入成本；
* 设计基于上下文的温和召回策略，防止用户一次吃超后彻底放弃；
* 召回默认 opt-in，并通过静默时段、冷却时间、重复保护控制打扰；
* 通过 OpenClaw 微信通道探索长期陪伴型 Agent 的触达边界。
